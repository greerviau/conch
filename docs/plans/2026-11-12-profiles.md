# Recording profiles

## Summary

Before this change, the recognition model, the recognition language, Enhanced cleanup, Auto-accept, and the repository selection were each one global setting.
A repository selected for a coding session stayed selected when the user later dictated prose elsewhere, so its identifiers reached the recognition hint and its suggestions reached the result.
Users with several repositories could not keep their contexts apart without toggling them before every recording.

A profile is a named set of those choices.
The user switches profiles on the Dictation page, from the menu bar icon, or on the recording indicator, including during a recording.
With one profile, which every install starts with, Conch looks and behaves as it did before.

This spec supersedes the statements in `2026-11-09-conch.md` and `2026-11-11-languages-and-recognition-engines.md` that place the recognition language, the recognition model, Enhanced cleanup, Auto-accept, and the repository selection in Settings, and the statement that a recording keeps the context it started with.
`docs/mockups/profiles.html` is the reviewed mockup.

## Requirements

- A profile has a name, a recognition language, a recognition model, an Enhanced cleanup choice (Disabled, Managed S1-mini, Local endpoint, or Remote endpoint), a set of repositories, and Auto-accept.
- Settings keep at least one profile and name one active profile. A new install has one profile named Default: English, Small (English), Enhanced cleanup Disabled, no repositories, Auto-accept off.
- Settings saved before profiles existed load as one Default profile that holds the saved language, model, Enhanced cleanup choice, selected repositories, and Auto-accept. Settings saved before the model choice existed keep Tiny (English), as before.
- These stay global: the shortcut, activation mode, microphone, Automatic paste, the floating indicator switch, Keep history, update checks, hesitation tokens (one list per recognition language), excluded literal terms, the cleanup endpoint and its model, the remote confirmation, and the API key.
- The shortcut is one global setting. Profiles have no shortcut of their own, so a switch during a push-to-talk recording never changes which key ends it.
- A recording uses the active profile. Switching during a recording applies to that recording: the audio heard so far is recognized and cleaned again with the new profile in the background, and the result is the same as if the recording had started with it. A switch after the stop, while the result is prepared, is refused.
- A profile whose recognition model is not installed cannot be chosen during a recording, because the recording cannot wait for a download. Between recordings it can be chosen, and the Dictation page asks for the download.
- A repository added on the Repositories page supplies context to the active profile only. A removed repository leaves every profile.
- Interface text states the action and its visible effect. It does not describe chunks, re-recognition, or workers.

## Interface

- Profiles page, between History and Repositories: the list of profiles with their model, cleanup, and repository count, and an editor with Name, Language, Recognition model with its download, Enhanced cleanup with the S1-mini download or the shared endpoint fields, the repositories with their term counts, Auto-accept, Make active, Duplicate, and Delete profile. The last profile cannot be deleted. Edits wait for Save changes.
- Settings no longer has Recognition, Enhanced cleanup, or Repository context rows, and says nothing about the move. Hesitation tokens edit the list of the active profile's language.
- Dictation page with one profile: the Context chips, as before. With more than one: a Profile card with the profiles as a segmented control, a summary of the active one, and the Context chips. Choosing a profile saves it at once. A chip changes the active profile's repositories.
- The setup checklist's Language and model menus change the active profile.
- Menu bar icon: the logo only, with no text. With more than one profile the menu has "Profile: name", whose submenu lists the profiles with a check on the active one and ends with Edit Profiles..., which opens the Profiles page.
- Recording indicator with one profile: unchanged, level bars and the time, and clicks pass through. With more than one, while recording: a person icon and the profile name follow the time. Clicking them opens the profile list above the pill; choosing one switches the recording and closes the list. Processing shows the spiral only and passes clicks through.

## Approach

`storage::Profile` holds a profile and `Settings` holds `profiles` and `active_profile`. `storage::snapshot` builds the context snapshot from the active profile. `Snapshot` carries the Enhanced cleanup choice beside the shared `Cleanup` values.

`pipeline::Transcriber` keeps the final audio of each chunk and of the tail. A `Switcher` sends it a new recognizer and cleaner; the transcriber abandons the old cleaner, recognizes the kept audio again with the new recognizer, and cleans it with the new cleaner, while later chunks queue behind. `app::switch_profile` saves the active profile and, during a recording, builds the new recognizer and cleaner, sends the switch, and replaces the recording's snapshot. The stop reads the latest snapshot for processing and Retry.

The indicator window grows to fit the profile name and grows upward to fit the list. It takes clicks only while it shows the name. On macOS a click must not activate Conch, or the app being dictated into loses its focused field: the window asks AppKit not to activate (`_setPreventsActivation:`, private, used only when the window responds to it), takes the first click without becoming key, and `platform::return_focus` reactivates the app that was frontmost when the recording started if Conch became active anyway.

## Validation

- Rust unit tests cover loading and normalizing profiles, migrating settings saved before profiles, the snapshot of the active profile, profile switching between recordings, during processing, and during a recording with and without the model, the transcriber's switch (re-recognition, re-cleaning, a switch after the tail, a switch after a failed chunk, a switch after finish), the indicator's profile list and window size, and the menu bar submenu.
- Frontend tests cover the Profiles page, the Dictation profile switcher and chips, repository assignment, the setup card writing the active profile, and the indicator's profile button and list.
- Untested: the macOS indicator click on an installed build. Whether a click on the indicator keeps the focused field of Chrome, a terminal, and an Electron app needs a manual test, because agent shells have no Accessibility trust. Windows and Linux indicator clicks are untested.
